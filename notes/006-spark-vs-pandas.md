# 기술노트 6 — 팩터 배치: 이 규모에서 Spark는 pandas보다 10.8배 느리다

## 무엇을 쟀나

`spark/factors.py`(모멘텀·변동성·거래대금 팩터)는 Week 1에 작성만 되고 실행된
적이 없었다. 동일 계산의 pandas 구현과 나란히 실행해 처리 시간을 쟀다.

```bash
uv run python scripts/bench_factors.py
```

## 결과 (price_daily 21,284행, 16종목)

| 엔진 | 시간 | 구성 |
|---|---|---|
| pandas | **0.55s** | 적재 0.53 + 계산 0.02 |
| PySpark (local) | 5.92s | 세션 기동 0.88 + 읽기·계산·쓰기 5.04 |

**Spark가 10.8배 느리다.** 두 결과는 20,964행 전부 동일하다(전 컬럼 최대
상대오차 3.2e-13). 결과가 같음을 확인하지 않은 시간 비교는 벤치마크가 아니라
서로 다른 프로그램 두 개를 잰 것이다.

## 왜 이게 정직한 결과인가

"Spark를 도입했다"를 성과로 쓰고 싶은 유혹이 있지만, 이 규모에서 Spark는
순손해다. JVM 기동, JDBC 파티셔닝, 셔플, 태스크 스케줄링 — 분산의 고정비용이
0.02초짜리 계산을 5초로 만든다.

Spark가 이기는 지점은 데이터가 단일 머신 메모리를 넘거나 파티션 병렬성이
고정비용을 상쇄할 때다. 16종목 × 5년이 아니라 전 상장사 × 20년(수억 행)
규모라면 곡선이 교차한다. **도구 선택은 규모의 함수이지 이력서의 함수가
아니다.**

노트 003의 ONNX와 같은 패턴이다 — "도입하면 빨라진다"는 통념은 측정 앞에서
자주 뒤집힌다.

## 공정성 장치

- pandas `rolling.std`는 ddof=1(표본)로 Spark `stddev`와 정의가 같다
- `min_periods=2`로 창 초입 null 처리를 Spark 윈도우와 정렬했다
- 두 결과를 (종목, 일자)로 조인해 전 컬럼을 수치 대조했다

## 실행 환경의 제약 (Windows)

호스트에서 PySpark는 `HADOOP_HOME unset` → `createTempDir` 실패로 죽는다.
해결책인 winutils.exe는 **Apache 공식 배포물이 아니라** 서드파티 바이너리다.
비공식 실행파일을 받는 대신 **공식 apache/spark:3.5.1 컨테이너**에서 리포
코드를 무수정으로 실행했다(`/work/src`를 sys.path에 추가).

측정 시간에서 컨테이너 이미지 풀과 Ivy 의존성 확보는 제외했다 — 재는 것은
잡 실행 시간이지 환경 준비 시간이 아니다. 단, pandas는 호스트(Windows)·
Spark는 컨테이너(Linux)라는 환경 차이는 남는다. 10.8배 차이를 뒤집을 수준은
아니다.
