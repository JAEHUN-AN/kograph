# 기술노트 1 — 관계 추출: LLM 대신 규칙 파서를 택한 이유와 실측

## 문제 정의

공시 509건에서 기업 간 관계를 추출해야 했다. 첫 설계는 LLM 구조화 출력이었다.
그런데 실행 직전 API 크레딧이 없다는 제약이 생겼고, 대안을 검토하는 과정에서
**원래 설계가 이 데이터에 최적이 아니었다**는 사실이 드러났다.

## 관찰: 대상 문서가 자유 서술이 아니다

DART 주요사항보고서 본문을 열어보니 고정 양식이었다.

```
3. 계약상대
(주)포스코
계약금액(원)
90,960,000,000
5. 계약기간
시작일
2026-07-01
```

라벨 줄 다음이 값 줄인 구조가 문서 전체에서 일정하다. 이런 입력에서는
정규식 파서가 LLM보다 **정확하다** — 환각이 없고, 결정론적이며, 동일 입력에
동일 출력을 보장한다. LLM의 강점(비정형 문장 이해)이 필요한 지점이 아니었다.

## 결과

| 항목 | 규칙 파서 | LLM (Haiku 4.5, 추정) |
|---|---|---|
| 처리 시간 | **0.4초** | 약 10분 |
| 비용 | **0원** | 약 $3 |
| 커버리지 | 396/509 (77.8%) | ~100% (비정형 포함) |
| 재현성 | 결정론적 | 샘플링 편차 존재 |

산출: 트리플 642개, Neo4j 노드 184개.

관계 유형 분포: `OFFICER_OF` 323, `SUPPLIES_TO` 85, `INVESTS_IN` 78,
`OWNS_STAKE` 70, `SUBSIDIARY_OF` 46, `GUARANTEES_DEBT_OF` 40.

**수치가 최초 기록보다 내려갔다.** 이 노트를 처음 쓸 때는 406건 / 662트리플 /
203노드였다. 이후 아래에 기록한 결함 수정(처분 공시 제외, 표 머리글·법인격
조각 유령 노드 제거, 개체명 정규화 병합)이 반영된 결과다. **커버리지가 떨어진
것이 개선이다** — 사라진 것은 애초에 틀린 관계였다. 지표를 올리는 방향으로만
움직이면 이런 수정을 하지 않게 된다.

## 커버리지를 64% → 80%로 올린 지점

1차 구현은 328건(64.4%)에서 멈췄다. 미파싱분을 유형별로 집계해 상위 항목을
역추적한 결과 세 가지 원인이 나왔다.

| 원인 | 실제 데이터 | 조치 |
|---|---|---|
| 라벨 변형 | `회사명` 아닌 `회사명(국적)`, 값도 `(대한민국)` 접미 | 라벨 추가 + 접미 제거 |
| 라벨 변형 | `계약상대` 아닌 `계약상대방` | 라벨 추가 |
| **관계 누락** | `자회사인 / <상호> / 의 주요경영사항신고` | `SUBSIDIARY_OF` 신규 추출 |

세 번째가 가장 컸다. 모회사가 자회사를 대신해 내는 공시가 미파싱분의 다수였는데,
여기엔 모자 관계가 명시되어 있었다. 더 중요한 건 **계약의 실제 주체가 제출사가
아니라 자회사**라는 점이다. 주체를 자회사로 바로잡지 않으면 그래프가 사실과
어긋난다.

## 테스트와 그래프 점검이 잡아낸 결함 4건

규칙 파서는 "돌아가는 것처럼 보이지만 조용히 틀리는" 실패에 취약하다.
합성 공시 텍스트 기반 단위 테스트와 적재 후 그래프 점검에서 4건을 잡았다.

**1. 다중 라벨의 우선순위 (테스트가 검출)**
`_field(lines, "채무보증금액(원)", "채무(차입)금액(원)")`가 인자 순서가 아니라
**문서 등장 순서**로 값을 골랐다. 차입 원금(3번 항목)이 보증액(4번 항목)보다
앞에 나와 엉뚱한 금액을 기록했다. → 인자 순서를 우선순위로 사용하도록 수정.

**2. 자회사 오탐 (테스트가 검출)**
자회사 판정 키워드에 맨 `자회사`/`종속회사`를 넣었더니, `회사와 관계` 항목의
**값**과도 매칭되어 존재하지 않는 자회사를 만들어냈다. → 공시 머리말 형태인
`~인`(자회사인/종속회사인)만 인정.

**3. 처분을 투자로 기록 (코드 리뷰가 검출)**
`타법인주식...처분결정`에 `INVESTS_IN`을 부여하고 있었다. 처분은 투자의
반대이므로 그래프가 사실과 정반대가 된다. → 처분 공시는 투자 엣지를 만들지 않고,
머리말에서 얻은 모자 관계만 남긴다.

**4. 표 머리글이 최다 연결 노드 (그래프 점검이 검출)**
적재 후 연결도 상위 노드를 뽑아보니 1위가 `생년월일 또는 사업자등록번호`(162개
연결)였다. `5. 최대주주등 주식소유현황(총괄현황)` 섹션은 라벨-값 쌍이 아니라
**표 머리글이 연속 나열된 구조**인데, 이를 라벨-값으로 오독한 것이다.
→ `4. 개인별 세부변동사항` 섹션 내부로 탐색 범위를 제한하고, 폼 라벨은 인명으로
채택하지 않는 안전망을 추가. 오염 엣지 162건 제거.

4번은 단위 테스트만으로는 못 잡았다. **적재 후 그래프 통계를 확인하는 절차**가
따로 필요하다는 교훈.

## 부수적으로 잡은 스키마 결함

`VARCHAR2(200)`은 기본이 **바이트** 기준이라 한글 상호가 약 66자에서 잘린다.
`ORA-12899`(actual: 292, maximum: 200)로 드러났고, `VARCHAR2(200 CHAR)`로 변경했다.
같은 에러를 추적하다 발행회사 칸에 **쉼표로 여러 회사가 나열되는 공시**(지분
일괄 처분)를 발견해, 회사별 트리플로 분리하도록 했다. 이때 금액은 건별 합계라
특정 회사에 귀속시킬 수 없으므로 대상이 여럿이면 금액을 비운다 — 복제하면
금액이 부풀려진다.

## 결론

LLM을 배제한 게 아니라 **적합한 자리에 배치**했다. 구조화 폼은 규칙 파서가
맡고, LLM은 남은 비정형 103건과 품질 벤치마크로 남긴다. `extract.py`의 LLM
경로는 그대로 살아 있어 `--model`만 지정하면 동일 평가셋으로 비교할 수 있다.

**남은 작업**: 미파싱 103건(유상증자 종속회사분, 신규시설투자 등) 파서 확장,
수동 라벨 200건으로 규칙 파서 정밀도 실측, 동일 셋에 대한 LLM 정밀도 비교.
